# Release Notes v0.6.0

Released: 2026-11-12

The project is now the **outcome model**: one document whose four views are
drawn as projections. **Causality** says why what you do should lead to the
change you want. **Strategy** says what you commit to and who owns it.
**Measurement and learning** says how you will know, and what you most need to
learn. **Improvement** says how you make a measured process better and keep the
gain.

This release fills out the strategy and measurement views. An outcome model now
exports a VSEM, an OGSM, a Balanced Scorecard, and a monitoring, evaluation, and
learning (MEL) plan, each from the model alone. The North Star and the one metric
that matters are both roles of a metric, checked alike, and the one metric that
matters is dated, period by period.

The rename and the dated one metric that matter break documents and Go code. See
[Upgrading](#upgrading).

## Highlights

- **The outcome model.** A new module path, command, document kind, schema
  names, and lint rule prefix. [ADR 0002](../design/adrs/0002-rename-to-outcome-model.md)
  records why.
- **Four new strategy and measurement exports.** `export vsem`, `export ogsm`,
  `export bsc`, and `export mel`, from the command line and the MCP server.
- **A strategy map from the causal links.** Outcomes placed in Balanced Scorecard
  perspectives become objectives, and the links between them become the
  strategy map.
- **Metric roles.** The North Star and the one metric that matters are checked
  alike, and the executive report and deck open with what each program steers by.
- **A dated one metric that matters.** Each pathway records what the team focused
  on in each period, and reports use the one for their date.

## New Features

### Four views of one model

The README and the documentation home now open with the four views, and group
the projections by view:

| View | Projections |
|------|-------------|
| Causality | Problem tree, theory of change, outcome map, logic model, logframe |
| Strategy | Balanced Scorecard, OGSM, OKRs, V2MOM, VSEM |
| Measurement and learning | MEL plan, metric tree, headline metrics, status |
| Improvement | DMAIC |

### Strategy exports

```bash
outcome-model export vsem outcome-model.yaml   # Vision, Strategy, Execution, Metrics
outcome-model export ogsm outcome-model.yaml   # Objective, Goals, Strategies, Measures
outcome-model export bsc outcome-model.yaml    # a Balanced Scorecard with its strategy map
```

Each writes a document in the matching [prism-roadmap](https://github.com/grokify/prism-roadmap)
`goals` format and links back to the model by ID. Each needs nothing beyond the
model, and refuses a model that lacks what the format needs, naming what to add.

| Export | Drawn from |
|--------|------------|
| VSEM | The vision and mission; one strategy per pathway, with the resources it commits; its interventions as execution, with owners and dates; its focus as metrics; the impact outcomes' indicators as the vision's metrics |
| OGSM | The objective (`context.objective`, or the one impact outcome), due at the end of the time horizon; its outcomes' indicators as goals; one strategy per pathway, serving the goals its outcomes lead to; its focus as measures; its interventions as actions |
| Balanced Scorecard | Outcomes placed in perspectives as objectives; the strategy map from the causal links between them; pathways as strategic themes; indicators as lead and lag measures; interventions as initiatives, with their resources as the budget |

The guides for [VSEM](../guides/vsem.md), [OGSM](../guides/ogsm.md), and the
[Balanced Scorecard](../guides/bsc.md) map each part of the format to the model.

### A monitoring, evaluation, and learning plan

```bash
outcome-model export mel outcome-model.yaml
```

The plan holds the results framework, the activities, an indicator reference sheet
for each indicator, the assumptions to monitor, the evaluation plan, the learning
agenda, the review meetings, and the reporting schedule. See the
[MEL guide](../guides/mel.md).

### New fields

| Field | What it holds |
|-------|---------------|
| `pathway.resources` | What a pathway commits as a whole: a name, an allocation, a description |
| `intervention.startDate`, `endDate` | When an intervention runs |
| `evaluations`, `learningQuestions`, `reviewMeetings` | The evaluation plan, the learning agenda, and the meetings that take it up |
| `indicator.qualityAssurance` and related fields | Data quality checks and caveats, for the reference sheets |
| `context.objective` | The one thing the model sets out to achieve, as a statement and the outcomes that say it has been reached |
| `outcome.scorecardPerspective`, `outcome.ownerActorId` | Where an outcome sits in a Balanced Scorecard, and who answers for it |
| `indicator.leadLag` | Whether an indicator leads or lags |
| `pathway.problemStatement`, `pathwayIds` on causes and effects | A problem tree for each program |
| `focus.oneMetrics` | The one metric that matters for each period |

### Metric roles

A metric's tier says where it sits in the chain from activity to impact. Its role
says what a team uses it for. The North Star, the one metric that matters, and
guardrails are roles, set on a pathway's `focus`.

```yaml
focus:
  northStarId: ind-retention-90
  oneMetrics:
    - indicatorId: ind-signups
      from: 2026-07-01
      to: 2026-12-31
      stage: acquisition
      reason: Too few accounts to learn from.
    - indicatorId: ind-first-week-recon
      from: 2027-01-01
      stage: activation
      reason: Most new accounts never reconcile a month.
  guardrailIds: [ind-support-load]
```

- **Dated focus.** The one metric that matters on a date is the entry whose period
  covers it; without a date, the one that started last. Periods must not overlap.
- **Changing focus.** `outcome-model pathway focus <file> <pathway> --one-metric
  <id> --from <date>` starts a new focus and ends the current one the day before.
- **Executive report and deck.** `report exec` and `deck exec` open with what each
  program steers by: its North Star and its one metric that matters, with status
  and progress against what was expected, and any guardrail that needs attention.
- **Metric tree.** It marks each role and lists the other periods' focus.

The [measurement guide](../guides/measurement.md#roles-north-star-one-metric-that-matters-and-guardrails)
explains tiers and roles, and why the North Star sits at or below the ceiling of
accountability rather than above impact.

### Lint

Lint has 83 rules, up from 72 in v0.5.0:

| Rules | Check |
|-------|-------|
| `OM-LRN-001` to `003` | Once evaluations or learning questions are planned, every high or critical assumption not yet shown to hold is taken up by one; open questions are taken up by a review meeting; dates fall within the time horizon |
| `OM-CTX-002` | A model with several impact outcomes names its objective |
| `OM-INT-008` | An intervention's dates fall within the time horizon |
| `OM-BSC-001` to `004` | The strategy map runs upward, and each scorecard objective is owned and measured by lead or lag indicators |
| `OM-NSM-008`, `009` | Each one metric that matters serves its own pathway, and leads to the North Star |

### DMAIC planning

`report dmaic-plan` plans a DMAIC effort before any data exists: the core problem
and its root causes, the interventions an improvement would change, and what each
metric still needs before `export dmaic` can chart it.

requires.

## Upgrading

### Install the new command

The command is `outcome-model`, from the new module path. The old `impact-model`
command is not kept; remove it from your path to avoid confusion.

### Documents

Change the kind, and the `$schema` if your files carry one:

```yaml
# was
$schema: https://github.com/ProductBuildersHQ/impact-model/schema/v0/impact-model.schema.json
kind: ImpactModel

# is
$schema: https://github.com/ProductBuildersHQ/outcome-model/schema/v0/outcome-model.schema.json
kind: OutcomeModel
```

A status snapshot's kind is `OutcomeModelStatus`, and its schema
`outcome-model-status`. Renaming files from `impact-model.yaml` to
`outcome-model.yaml` is optional, but it is the name the commands and examples use.

A pathway's `focus.oneMetricId` becomes a dated entry. Use the date that focus
began:

```yaml
# was
focus:
  oneMetricId: ind-first-week-recon

# is
focus:
  oneMetrics:
    - indicatorId: ind-first-week-recon
      from: 2027-01-01
```

Nothing else in a document changes; `specVersion` stays `"0.1"`.

### Command line, MCP, and skills

| Was | Is |
|-----|----|
| `impact-model …` | `outcome-model …` |
| `pathway set --one-metric <id>` | `pathway focus --one-metric <id> --from <date>` |
| Lint rule IDs `IMP-STR-001` | `OM-STR-001`; update any `--disable` lists |
| MCP tools `impact_validate`, `impact_export`, … | `outcome_validate`, `outcome_export`, … |
| Agent skills `impact-author`, … | `outcome-author`, … |

An MCP client configured with the old server name or tool names needs the new ones.

### Go code

Every import path changes, and two packages are renamed:

| Was | Is |
|-----|----|
| `github.com/ProductBuildersHQ/impact-model/...` | `github.com/ProductBuildersHQ/outcome-model/...` |
| `pkg/impact`, `impact.Model`, `impact.Outcome` | `pkg/model`, `model.Model`, `model.Outcome` |
| `pkg/impactio`, `impactio.LoadDocument` | `pkg/modelio`, `modelio.LoadDocument` |
| `impact.KindImpactModel` | `model.KindOutcomeModel` |
| `schema.ImpactModel` | `schema.OutcomeModel` |
| `Focus.OneMetricID` | `Focus.OneMetrics`, and `Focus.OneMetricAt(date)` for the one on a date |

The rest are additions, among them `prismx.ToVSEM`, `ToOGSM`, `ToBSC`, `ToMEL`
and their `ErrNot…Ready` errors, `report.Steering`, `report.DMAICPlan`,
`edit.FocusOn`, `problemtree.BuildFor`, and the Balanced Scorecard accessors
`Model.ScorecardObjectives`, `ScorecardContributesTo`, and
`ScorecardObjectivesServed`.

## Compatibility

v0.3.0 to v0.5.0 stay published under `github.com/ProductBuildersHQ/impact-model`,
and GitHub redirects the old repository address. Because the module path changed,
no Go code compiles against both without changing its imports. Apart from the
renames above and `focus.oneMetricId`, a v0.5.0 document needs no changes, and the
command line keeps its exit codes.

## Known Limitations

- **Only the one metric that matters is dated.** The North Star and guardrails
  hold one value each.
- **The Balanced Scorecard export leaves out thresholds and the strategy
  statement.** The model holds neither; add them to the exported scorecard.
- **An export refuses a model that lacks what its format needs** rather than
  writing a partial document. The message names what to add.
- The limitations of [v0.5.0](v0.5.0.md#known-limitations) still apply.
